# 工程票 M7.2：任务与 Study 标识必须带上运行 id

2026-08-07 立。前置：M6、M7.1。触发它的是第二次真实模型运行**只跑了一轮就停**。

## 事实

修完 M7.1 之后重启服务，`--max-rounds 12`，结果：

```json
{"stopped_because": "no_runnable_work", "rounds": 1, "distinct_features": 1,
 "infrastructure_failures": 0, "episodes": 2}
```

原因是队列与账本都跨运行持久，而标识不带运行 id：

```python
task_id = f"auto-task-{index}"
study_id = f"auto-study-{index}"
```

第一次运行已经用掉了 `auto-task-0` 到 `auto-task-7`。第二次运行入队 `auto-task-0`
时它恰好还是 `ready`（第一次运行的第 0 轮解析失败被重排过），因此那一轮跑了；
入队 `auto-task-1` 时它已经是 `done`，入队成了空操作，于是「无可执行工作」。

**同一个缺陷更糟的一面**：`auto-study-N` 也会撞。两次运行的证据会被写进同一个
Study 标识下，`collect_snapshot` 按 study_id 收集事件，因此快照会把两次运行的
提案、冻结、判决混成一份。这次没暴露出来只是因为服务停得早。

## 改法

`run_service` 新增 `run_id` 参数（默认 `"auto"`），进入任务、Study 与 Episode 的标识。
`run_service_demo` 把 CLI 的 `--run-id` 透传下去 —— 那个参数此前只用于 Atlas 的
运行目录命名，没有进入证据标识。

## 两处顺带修掉的、同属一类的问题

**一、`--run-id` 缺省时兜底发生得太晚。**时间戳兜底原本写在 `run_service_demo`
函数末尾，只为 Atlas 的运行目录命名。因此缺省调用时 `run_service` 拿到的是 `None`，
任务标识变成恒定的 `"None-task-0"`，本票要修的冲突原样回来。兜底移到服务启动之前，
有测试按源码顺序钉住。

**二、`no_runnable_work` 是唯一一个能由缺陷触发、却读起来像干净完成的停止理由。**
标识冲突时入队静默成空操作，服务写下 `no_runnable_work`、**不写**
`human_review_required`、退出 0。第二次运行就是这样被丢掉的，而我只是因为读了
输出才发现。这与把 `parse_failure` 计进停滞、以及用 `blocked` 吞掉 null
是同一类错误：把缺陷报成结论。

改为入队前检查标识是否已存在，存在则抛 `TaskIdentifierCollision`。
刻意抛异常而不是记一条停止理由：让它响，比让它安静地退出 0 好。

## 实测

新增测试在同一个队列与账本上连跑两次，断言两次都跑满轮数、四个任务标识互不相同、
两次的 `runA-study-0` 与 `runB-study-0` 都出现在账本里。
改动前该测试的第二次运行会以 `no_runnable_work` 停在第 0 轮。

`.venv/bin/ruff check .` 通过；`pytest tests/ -q`：**642 通过**。

## 本票不做

- 不清理既有账本里的 `auto-*` 标识。账本只增不改；那些记录按当时的语义成立，
  且第一次运行的八轮全部落在 `auto-study-0..7` 上，没有实际混淆；
- 不改 Atlas 的运行目录布局。
