# 工程票 M6.1：真实模型跑起来之后暴露的三件事

2026-08-07 立。前置：M6 连续研究服务、M5.3 菜单加宽。触发它的是第一次
`--provider claude` 实跑，不是设计推演。

## 事故

第一轮耗时 8 分钟、3 次调用，全部解析失败。账本里 `parse_failure` 记着最后一次的错：

```
1 validation error for ProposalOutput
direction
  Input should be a valid integer, unable to parse string as an integer
  input_value='positive'
```

只有一条校验错误，意味着那一次的 `feature_spec` 整个是合法的 —— 模型把机制、
可证伪条件、两步 innovation + zscore 都写对了，栽在一个顶层字段的类型上。

`output_contract` 当时只列了字段名，没列类型。合同没写全，然后指责对方违约。

## 三处修正

**一、契约写出类型（`context.py`）。**新增 `PROPOSAL_OUTPUT_TYPES`，逐字段给类型，
其中 `direction` 明写「整数，只能是 1 或 -1，不接受 "positive" 这类词」。
有结构测试钉住它与 `ProposalOutput.model_fields` 一致，与既有的
`STEP_SCHEMA` 测试同形，因此不会再漂。

**二、封闭同义词表（`episode.py`）。**`{positive, negative, long, short, up, down}`
规范化为 ±1。这不是宽容：映射封闭、确定，账本记下的仍是整数。
**表外的词必须整条报错** —— `direction` 为 None 时 `to_proposal()` 写成 0，
于是一条 `falsifiable_condition` 写着「为正」的提案会带着「无方向主张」通过，
预注册就成了空的。宁可整条被拒。

**三、逐次记错（`providers/base.py`）。**`ParseFailure` 原本只存 `last_error`，
因此那 8 分钟里前两次错在哪已无从查起。改为逐次记入 `attempt_errors`，
并记 `raw_length`：摘录截在 500 字，截断与格式错误在摘录里长得一模一样。

## 第四件，也是更要紧的一件：停止语义被污染

`run_service` 原本对每一轮算「有没有产生新的特征内容身份」，没有就 `stale += 1`。
解析失败的一轮既没有 `proposal_id` 也没有 `feature_id`，于是**它被算成停滞**。
按 `stall_rounds=3`，上面那个 schema 缺陷再多两轮就会让服务写下
`human_review_required` 说「模型问不出新东西了」。

这与此前按 `proposal_id` 计新颖性是同一类归因错误：把工程缺陷读成研究结论。

判据不是「失败得像不像工程问题」，而是**这一轮有没有形成过提案**。
`parse_failure` / `provider_error` / `context_blocked` / `invalid_proposal`
四种结局都在 `record_proposal` 之前返回，对「还有没有新问题可问」不构成任何证据。
它们现在单独计入 `infrastructure_failures`，连续 `stall_rounds` 轮则以
`provider_unusable` 停止，写下的复核理由明说「不构成关于该机制族的任何研究结论」。

两种停法要人做的判断不是一回事：一个问「还值不值得继续找」，
一个说「执行者根本没产出可解析的东西」。

## 实测

同一次运行修复前的后续轮次证明通道本身是通的：第 2、3 轮各经一次修复重试后
解析通过，走完了完整判决。模型自主从 30 个族的菜单里选中 `cand:iran`
（菜单不含任何指向原油的提示），构造

```
iran_notional_innov   = innovation(pm_market, cand:iran:notional, sum,
                                   window=86400s, baseline=2592000s, offset=3600s)
iran_notional_innov_z = zscore(iran_notional_innov, window=7776000s,
                               sample_every=86400s, min_samples=30)
```

并在 `failure_condition` 里写下四条证否路径，其中一条预判了预热期造成的样本不足。

两轮判决都是 `blocked`，理由一致且成立：置换检验 0.980 / 0.880（实际斜率不比
置换斜率更极端），最大 DFBETA 占斜率 9.72 / 4.84（预注册上限 0.5）。
1040 行里 534 行按预注册剔除，余 506 行进入检验 —— 模型自己写下的失效条件 (1)
正好预判了这个缺口。诚实的说法是「一个离群日撑起了整条斜率，且样本本就偏短」，
不是「这个机制死了」。

- `.venv/bin/ruff check .` 通过；
- `.venv/bin/python -m pytest tests/ -q`：**619 通过**（基线 613 + 本票 6）。

## 本票不做

- 重尾回归元的盲化诊断通道（见下条阻塞事项）；
- `proposal_recorded.family` 记的是 Study 族而不是特征所用的 pm 族，
  属标注缺陷：族在一次服务运行内恒定，零假设带的累积不受影响。

## 新增阻塞事项

**重尾回归元没有反馈通路。**连续两轮死在 DFBETA 上，而 `blocked_reasons`
按盲化白名单不进提案器上下文（`verdict_recorded` 只放 `study_id` 与 `verdict`），
因此模型无从知道问题出在特征的分布形状上，只会继续产出同样重尾的名义成交额特征。
可行的解法是**只用 X、不碰 y** 的特征健康诊断（偏度、峰度、最大单点占比），
它与语义审计同属读 outcome 之前的通道，因此不构成在检验统计量上爬山。
另立一票。
