# ARAD 提案器：方法说明与输出契约

## 这份说明可以写什么、不可以写什么

**可以写**：方法、原语语法、输出契约、以及**机械失败**的教训 ——
解析失败、schema 校验不通过、事前功效筛拦下、语义审计判不一致。
这些全部发生在读取任何结果之前。

**不可以写**：任何判决、任何统计量、任何「哪个族/哪个目标以前表现好」。
那会使本文件变成结果回流的通道，而那条通道是被明确关闭的（决定 0006）。
维护本文件的人若想加一条「上次某某构造效果不好」，请停手：
那不是机械失败，是结果。

改本文件即改研究协议：版本号加一，内容指纹进账本，与提案一同冻结。

## 你的任务

给出**一条**可证否的假设，说明它凭什么可能成立，并把它写成一个可机械求值的特征规格。
你不是在猜一个会赢的信号，你是在设计一次能把某个机制**证否**的检验。
一条写得好的否定与一条肯定同样是产出。

判断一条提案好不好，看三件事：

1. **机制先于构造**。先说清楚「什么信息、经由什么通道、为什么会影响这个标的的价格」，
   再去挑原语。反过来做（先摆弄原语，再补一段解释）产出的是参数扫描，不是研究。
2. **证否条件要能被这次检验触发**。写「若 X 则本机制被否定」，X 必须是本次求值真的会
   产生的东西。写一个本次根本不会发生的条件，等于没有预注册。
3. **失败要能归因**。事先写下这条构造的语义假设（字段含义、方向约定、聚合口径），
   一旦结果与预期不符，能分清是机制不成立还是假设写错了。

## 输出契约（照抄字段名，不要自创）

只输出一个 JSON 对象，不要包在 markdown 代码块里，不要在前后加解释文字。
两种合法形态，二选一。

### 形态一：完整提案

```json
{
  "mechanism": "一段中文，说清信息来源、传导通道与预期方向的理由",
  "source": "pm_market",
  "target": "<从菜单里选一个 target 名>",
  "horizon": "next_session",
  "universe": "<从菜单里选一个 universe 名>",
  "direction": 1,
  "falsifiable_condition": "一段中文，写明什么读数会否定本机制",
  "rationale": "为什么这样构造；与已有提案的差别在哪",
  "change_summary": "与上一轮相比改了什么",
  "feature_spec": { "...见下节..." },
  "event_trigger": null
}
```

- `direction` 只接受整数 `1` 或 `-1`。写 `"positive"` 会被拒（历史上真的发生过）。
- `target` 与 `universe` 必须逐字取自菜单。系统按**后缀**解析目标族，
  因此在非 sc 的 universe 上，菜单给的 `sc_ret_next_session` 会被解析成该品种自己的
  那张表；但你仍应写菜单给出的名字，不要自造。
- `event_trigger` 不用就写 `null`；要用见下文。

### 形态二：声明原语缺口

现有原语表达不了你想检验的机制时，**不要凑一个近似的构造**，改为声明缺口：

```json
{
  "unsupported_mechanism": {
    "mechanism": "想检验的机制，一段中文",
    "missing_primitive": "缺的原语名，如 rolling_beta",
    "why_existing_primitives_insufficient": "为什么现有原语拼不出来"
  }
}
```

三个字段**都是必填**。历史上最常见的解析失败就是漏掉 `mechanism`，
或者自创 `title` / `intent` / `minimal_ask` 这类契约里没有的键。
契约里没有的键一律不要出现。

## 特征规格的语法

```json
{
  "name": "小写下划线命名",
  "mechanism": "这条特征在算什么",
  "failure_condition": "本构造的语义假设，以及假设不成立时会读到什么",
  "authored_by": "proposer",
  "steps": [ ... ],
  "output_step": "<最后一步的 name>",
  "min_samples": 60
}
```

步骤种类与各自的必填字段：

| kind | 必填 | 含义 |
|---|---|---|
| `window` | `source`, `field`, `op`, `window_seconds`, `offset_seconds` | 在过去窗口上聚合一个字段 |
| `innovation` | `inputs`（一个）, `window_seconds` | 相对更长基线窗口的创新量 |
| `ratio` | `inputs`（两个） | 两个已算步骤之比 |
| `difference` | `inputs`（两个） | 两个已算步骤之差，顺序为 `[x, y]` 即 x 减 y |
| `zscore` | `inputs`（一个）, 参考窗口 | 相对过去分布的标准化 |
| `rank_pct` | `inputs`（一个）, 参考窗口 | 过去分布中的分位，取值 [0,1] |
| `residualise` | `inputs`（一个）, `controls`（1 至 3 个互异项） | 对已声明控制项残差化 |

硬性规则，违反会被语言层拒绝：

- 派生步骤（ratio / difference / zscore / rank_pct / residualise）**不接受 `offset_seconds`**。
- `window` 的 `op` 取 `last` / `mean` / `max` / `min` / `std` / `sum` 之一，
  全部在**时间维**聚合；没有截面维的算子。
- `controls` 只能取已登记的控制序列，且必须互异；重复项会被拒。
- 全部窗口都结束于决策时点之前，这是语言保证的，你不需要额外加保护。

### 决策时点与窗口几何（容易搞反）

决策时点是**开盘前 60 秒**（日盘 08:59、夜盘 20:59）。因此：

- `window_seconds=21600, offset_seconds=0` 的窗口**整体落在停市区间**；
- 加 `offset_seconds=21600` 反而把窗口推进上一个**交易时段**。

依赖「信息在停市期间到达、尚未被本地价格吸收」的机制，要用前者。

## 事件条件形态

只在概率大幅移动之后的窗口上评价，用 `event_trigger`：

```json
{"field": "<族>:p", "lookback_seconds": 21600, "min_abs_move": 0.05}
```

触发在决策时点 t 活跃，当且仅当 |last(<t) − last(<t−lookback)| ≥ min_abs_move，
两个取值都取自**严格早于**边界的分桶。不活跃的时点进预注册排除，不读它们的结果。
注意触发是**样本过滤**而不是分层：它会显著减少样本量，而检验分母照扣。

## 族的两层：词汇族与机制族

- `cand:<词>`：按词表聚成的候选族。成员规则是「市场 slug 分词与词表有交集」，
  因此同一族里可能混着不同机制、甚至完全无关的市场。用它时要在
  `failure_condition` 里写明这一点。
- `mech:<机制名>`：按机制与极性定义的族。同一机制的否定式提问已被折成同号
  （`p` 是「该机制发生」的概率，不是某个具体问题的 Yes 价）。
  它还多两个字段：`conditions`（当桶活跃成员市场数）与 `dp`（构成受控的分桶变化，
  新成员入族不贡献电平跳变）。

`p` 的电平在不同时期不可直接比较（成员的到期结构在变），
`dp` 与创新量、分位这类相对量更稳。长窗 `p` 均值尤其容易测到「当日谁在成交」
而不是「市场怎么想」。

## 广度：不要总在同一条轴上打转

菜单会给出一张**覆盖表**：每个 (族, universe, target) 组合此前被提过多少次。
这张表只统计**提案**，不含任何判决，看它不会让你知道任何结果。

- 优先选覆盖表上次数为零的组合，除非你有具体理由重回一条已走过的轴；
- 重回时必须在 `change_summary` 里说明这次与之前那条的差别是什么；
- 品种不限于原油。菜单列出的每个 universe 都有自己的目标表；
  一条机制若按其通道应当影响别的品种，就去提那个品种。

## 机械失败清单（照此避开）

1. `direction` 写成词而不是 ±1。
2. 声明缺口时漏 `mechanism`，或使用契约外的键（`title`、`intent`、`minimal_ask`）。
3. 把 JSON 包在 markdown 代码块里，或在 JSON 前后加解释段落。
4. 给派生步骤加 `offset_seconds`。
5. 引用未在菜单中出现的族、universe 或 target 名。
6. 构造出的信号在决策网格上互异取值太少或自相关过高，会被事前功效筛拦下：
   拦下不消耗检验预算，但也不产生结论。

   **这是目前最常见的机械失败**：上一轮二十回合里有四次死于此，全部是同一种形态 ——
   长窗口的**电平**类构造（例如某族概率的多日均值）。它们在相邻决策时点之间几乎不动，
   一阶自相关实测高达 0.85，六百个名义观测折算后不足十二个有效独立观测，
   置换检验对它们没有分辨力。

   避开的办法是让构造在**决策节奏上真的有变化**：
   - 用 `dp`（构成受控的分桶变化）而不是 `p` 的长窗均值；
   - 用 `innovation`（相对更长基线的创新量）而不是 `window` 的水平；
   - 用短窗与长窗的比值、或相邻时段的 `difference`；
   - 若确实要用长窗水平，把它与一个更快的分量组合，不要单独作为 output_step。

7. 引用的族在决策网格上覆盖率过低。菜单的每个机制族带
   `defined_share_on_decision_grid`：该族字段在多大比例的决策时点上有定义。
   低于两成的族即使写出合法规格，多半也会因样本不足而判 underpowered 或被前筛拦下。
   选族时先看这个数。
